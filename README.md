# ESTADEL · Мониторинг интеграций

Локальный прототип для разбора тестовых вебхуков. Журнал показывает время, источник, тип, статус и описание события. Счётчики охватывают весь журнал, фильтр переключает видимые строки, а детали показывают полное описание и идентификатор события. Нажмите «Время» в заголовке таблицы, чтобы переключить порядок событий. На узком экране сортировка доступна над карточками журнала.

## Запуск

Нужен Node.js 22 или новее. Запустите приложение из каталога репозитория.

```sh
npm start
```

Откройте [http://127.0.0.1:3000](http://127.0.0.1:3000). При необходимости смените порт через `PORT=3001 npm start`. Проект использует встроенный HTTP-сервер Node.js и нативные HTML, CSS и JavaScript. Установка зависимостей не требуется.

## Добавление события из журнала

Нажмите «Добавить тестовое событие», укажите источник, тип, статус и описание. Для статуса «Ошибка» опишите причину. После сохранения запись появится в журнале с учётом выбранной сортировки. Если выбранный фильтр исключает новый статус, журнал переключится на «Все».

Чтобы увидеть отправку в браузере, откройте вкладку Network в инструментах разработчика перед сохранением и выберите `POST /api/events`. В запросе видны отправленные поля, в ответе `201 Created` — созданное событие с ID и временем.

## Демонстрация API

`GET /api/events` возвращает `200 OK` и массив событий в порядке поступления, начиная с новых. Каждое событие содержит `id`, `source`, `type`, `status`, `created_at` и `message`.

```sh
curl -i http://127.0.0.1:3000/api/events
```

`POST /api/events` принимает JSON с четырьмя обязательными строковыми полями. `source` и `type` содержат до 80 символов, `message` до 500, а `status` принимает значение `success` или `error`. Строки очищаются от крайних пробелов. Для ошибки укажите причину в `message`. Сервер задаёт `id` и `created_at` в UTC и игнорирует дополнительные поля.

Успешный запрос возвращает `201 Created` и сохранённое событие. Откройте фильтр «Все» или «Успешно», чтобы увидеть событие после автообновления журнала. Кнопка «Обновить» загружает его сразу.

```sh
curl -i http://127.0.0.1:3000/api/events \
  -H 'Content-Type: application/json' \
  -d '{"source":"Тестовый вебхук","type":"lead.created","status":"success","message":"Тестовая заявка принята"}'
```

Без `message` сервер возвращает `400 Bad Request` с пояснением в `error.fields.message`. Число событий остаётся прежним.

```sh
curl -i http://127.0.0.1:3000/api/events \
  -H 'Content-Type: application/json' \
  -d '{"source":"Тестовый вебхук","type":"lead.created","status":"success"}'
```

Сервер также возвращает `400` при некорректном JSON, `413` для тела больше 16 КиБ и `415` для запроса без `Content-Type: application/json`.

## Проверки

```sh
npm test
```

Тесты поднимают отдельный HTTP-сервер и проверяют стартовые данные, добавление события, валидацию и сохранность журнала при отклонении запроса.

## Допущения и ограничения

- При запуске журнал заполняется вымышленными событиями. Новые записи живут в памяти до перезапуска процесса.
- Сервер доступен локально через `127.0.0.1`. Прототип рассчитан на работу с тестовыми данными.
- Журнал показывает время в МСК. Открытая вкладка опрашивает API каждые пять секунд и позволяет обновить список вручную.
- Автообновление загружает журнал целиком. Размер набора данных рассчитан на демонстрацию.

## Подход к реализации

Один снимок API питает и счётчики, и журнал, поэтому они согласованы после каждого обновления. Глобальная статистика сохраняет общий контекст, пока оператор разбирает ошибки в отфильтрованном списке.

Использован OpenAI Codex. Отдельные субагенты реализовали интерфейс и API с тестами, третий выполнил независимое ревью. Оркестратор зафиксировал контракт, провёл интеграционную проверку и собрал локальную историю Git.
